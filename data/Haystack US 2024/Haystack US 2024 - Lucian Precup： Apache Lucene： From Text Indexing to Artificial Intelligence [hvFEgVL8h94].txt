The basis of Apache Lucene is the inverted index, which you likely already know about. I want to refocus on that because it's where everything started. Lucene's analysis chain is another core functionality. Tokens aren’t added to the index as they are; they go through this chain. For example, we lowercase capitals, and employ stemming to treat plural and singular forms like "cars" and "automobile." We also use synonyms; Lucene can understand "automobile" and "car" are synonyms. We can use stopwords like "of," "on," etc., as they're often non-relevant. The resulting data structure is highly optimized for performance and boolean queries. Searching for a term like "automobile" is fast, as you can directly access pointers to the relevant documents.

Apache Lucene had additional structures even in its first versions because metadata and support for phrases were needed. It didn't just handle the simplest of structures. The syntax persists today, available in user interfaces like Kibana and OpenSearch dashboards. You can perform field searches, phrase searches, approximate searches, etc. Some features weren't available at the start, but Lucene evolved.

Text analysis in Lucene is fundamental. It allows text to be analyzed at both index and query time, making it fast. This is exemplified in an autocomplete service; initially, it used wildcard searches that required full index scans, which were slow. By introducing n-grams, the index became bigger, but with compression, Lucene was able to construct an index with the original text file’s size while adding functionality. The analysis chain can differ between index and query times, which adds utility.

Lucene's efficiency improved with fuzzy queries. The integration of finite automata like FSA and FSTs optimized them significantly, achieving up to 100 times faster query speeds. Such performance boosts were transformative and extended to other Lucene features. More data is indexed for efficient searches, which steadily increased Lucene's capabilities.

In e-commerce, we realized Lucene needed numeric support. Early Lucene was text-oriented, and numeric sorting (like product prices) required text workarounds, which could be inefficient. Early experiments storing integers show Lucene's adaptability to space and performance requirements. Term facets, range facets, hierarchical facets: these enabled detailed queries and drove Lucene's data inversion innovations. Doc values arose from these needs and introduced relational database concepts such as runtime joins. Features like document blocks and field collapsing were instrumental in e-commerce use cases.

Lucene became viable for geographic searches, despite initial challenges. As polygons required integer use previously unsuitable, Lucene introduced Geo shapes, bounding box queries, and other spatial features, achieving market dominance as a spatial database. Massive monitoring and observability use cases validated its utility, comprising most existing use cases for Elasticsearch and OpenSearch today.

Vector indexing and search moved Lucene into modern AI paradigms, accommodating text, image, and audio searches by forming multi-modal vector spaces. Supporting both dense and sparse vectors, Lucene found compatibility with its inverted index roots. Dense vectors empowered by K-Nearest Neighbors (KNN) accelerated search capabilities, introducing hybrid search elements with filters. Sparse vectors, facilitating term expansion and fuzzy querying, offered efficient querying solutions.
