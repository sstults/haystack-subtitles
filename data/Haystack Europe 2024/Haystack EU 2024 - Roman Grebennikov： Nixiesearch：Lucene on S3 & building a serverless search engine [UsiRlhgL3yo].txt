Then you come back to work and start spinning the wheel of reality, operating your search engine, which actually generates the revenue that pays your salary. This picture started out as a joke, but it actually summarizes all the incidents I faced with operating search engines. It's not about a specific search engine; it's about the whole class of search engines we currently run in production.

Search engines are considered special. They're more databases than anything, a stateful application that depends on permanent storage. They have problems with scaling up and down because you need to rebalance states if something goes wrong with your storage, which can lead to issues. But if you reflect back on backend applications, they tend to be simpler. You have your application and compute resources separate from your state. You can do things like modern rollbacks, blue-green deployments, A/B tests, scale-ups, and scale-downs more easily because the state isn't managed by you. This convenience makes operations and modifications much easier.

However, the issue with current search engines is that this complexity extends beyond the search engine itself, into your search and indexing pipeline. So if you change something in your index, you also need to update this pipeline, which increases the overall complexity of running your search engine. If I were a search engine vendor, I would embrace complexity because it helps sell managed services. But since I'm more of an operator, I'm trying to reduce complexity to make my life easier.

You might wonder if search engines can be stateless, more like backend applications and less like databases. There are several projects already taking this angle, like Elasticsearch, which is a Yelp search engine, and it's not very popular. It’s implemented on top of Lucene with real-time replication. OpenSearch offers segment replication over remote storage, not fully stateless, but a step towards decoupling. In other areas, there’s Quikwit, a search engine for logs and telemetry, and Turbopuffy, a vector search engine that runs over block storage.

The strategy behind these engines is to decouple search, compute, and storage, leading to easier operations and cheaper costs. In various industries, Amazon's talk on 'Buzzwords' and similar works from Uber and Doordash point towards this decoupling trend where indexers update segments on S3, and searchers pick those segments up. Even at my past company, we moved from Elasticsearch to Lucene, inspired by these insights.

But, are these engines open-source? No. So companies must often create their own versions. That's what led to Nixiesearch. There seemed to be a demand, so we thought: "Why not write our own search engine?" It started as a proof of concept, running Lucene over block storage, and evolved into something more. If you look into Lucene and block storage, you might find a blog post by Shay Banon, creator of Elasticsearch, pondering using Lucene over S3—this was about 15 years ago. While unfinished, it laid the groundwork for considering non-traditional block storage.

Lucene was tricky to extend, as it originally worked with block storage locally, not remotely, like S3, which has higher latency. Latency tests showed it's about 10 to 20 milliseconds for Amazon's S3. We approached this by caching locally, reducing repeat fetch times and allowing for easier scaling of stateless nodes across multiple services.

However, initial request times were high due to necessary data access across S3, so we implemented a caching proxy between Lucene and block storage. Two types of S3 endpoints were considered, traditional and S3 Express. The latter offers faster response times at reduced redundancy. Ultimately, this improved performance significantly, yet initial latency remains a challenge for vector searches due to inherent complexities in graph traversal.

In practice, configuration files make index creation simple and integrate CICD system checks to ensure compatibility with existing datasets, providing a backend-like deployment. This segmentation allows for consistent index updates without service disruption, using a decoupled approach of indexing separately from runtime search traffic, potentially saving on costs by not running indexers continuously. We support indexing remotely with auto updates, providing a seamless search experience, with familiar interfaces for queries and dataset management, while allowing for local inferencing.

Some limitations include the absence of sharding due to stateless design, and indexing large datasets may take longer initially. Further improvements aim to expand model incorporation directly into search algorithms. Ideally, containerized environments allow for seamless local setups with minimal dependencies, reinforcing decoupling for broader industry adaptability.

**Audience Member 3:**  
You mentioned continued latency issues on reads due to design leaning towards a read-through cache rather than prefetching everything. Can you elaborate on this?

**Roman Grebennikov:**  
Our cache is indeed read-through, so initial reads are slower until caching kicks in. We're aiming for improvements here, possibly through IO-level parallel prefetching. When done locally, the latency is negligible for most reads, but S3’s initial latency transport remains a challenge without prefetch invocations.

**Audience Member 4:**  
Is Nixiesearch meant to be run as a Lambda, or on EC2?

**Roman Grebennikov:**  
Technically, it could work as a Lambda, though startup times involving index fetching might be prohibitive. It can definitely be run on EC2, which would better handle continuous workloads. For ingestion, batch jobs may suffice depending on the latency requirements of your indexing operation.
