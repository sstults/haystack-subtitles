With this strong justification, or at least I hope, I will move on to the UBI goals. The goals for UBI are to collect data. UBI enables you to collect data; you own the data, so you control the data. You're not giving the data to anyone. Let me put it out there, so with UBI, you can measure what searches are being done. Did the user use the type-ahead feature? Evaluation tools, A/B testing, and creating judgment lists are options, but measuring and tracking user behavior is the source for anything you are doing. That is why UBI.

UBI provides, at its core, a standardized schema. It also provides client-side instrumentation, a bunch of JavaScript tools, and means to collect and analyze the data. Zooming into the technicals, at least in OpenSearch right now, UBI is represented as two indices: the query index and the events index. The queries index logs the search queries, while the events index captures click metrics. I hope this is legible enough. The standardized schema for the queries index includes a client ID, the entire search query, query attributes such as application name, a query ID which tracks the user journey, the response ID hits indicated by document IDs returned, timestamps, and the user search term.

For the events index, fields like action name capture user interactions such as facet clicks and type-ahead uses. The index also includes application type, client ID, event attributes, and message details of the search result clicked, correlating with the query ID from the queries index and timestamp. Both these indices can be viewed as time-series data due to included timestamps. The events attributes section serves as a flexible area to capture anything else that you want, but balance is needed here to avoid mapping explosion issues.

Let’s move forward to the integration of UBI with OpenSearch. UBI in OpenSearch is a plugin that requires installation. A search is performed, and the plugin identifies and logs the search request into the UBI query index, including the document IDs returned. For user activities such as clicks, client-side instrumentation logs these into the UBI events index. Data can be directly sent to OpenSearch or go through Data Prepper for larger scale operations, allowing merging of sensitive backend data when needed. 

Going to a demo: in OpenSearch Dashboards, go to the tools section to issue API calls to interact with OpenSearch. Installing the UBI plugin results in the creation of the queries and events indices using a standardized schema. Now populating these indices involves making standard search calls including a UBI clause with query ID, user query, client ID, and query attributes like application name. On the events side, this is handled by the frontend using APIs to log actions into the events index.

Once data is ingested, analysis is the next step. The OpenSearch dashboard provides visualizations like pie charts indicating user actions, session duration, and financial metrics based on user queries and event data. With SQL handler support in OpenSearch, anyone familiar with SQL can interact with the data in an ad-hoc manner. This makes it easier for stakeholders familiar with SQL to extract meaningful insights without waiting for visualization efforts. 

UBI also helps create a judgment list needed for implementing secondary re-rankers like learning to rank strategies by joining queries and events indices, grading document interactions into relevance categories. Though OpenSearch SQL currently cannot fully handle these SQL requirements, the idea has been presented showing potential practical implementations via Hadoop client usage.

As data grows, cost management is important. OpenSearch allows warm nodes for older data and transforms to summarize aging data, cutting storage costs while retaining essential analytics potential. The NAV sensors allow alerting for search behavior anomalies like an absent trending product.

Finally, the idea of UBI is not limited to OpenSearch alone. While current dependency exists on OpenSearch for the queries index, UBI can still be used with other search engines to handle events logging and streamline processes, merging search results data subsequently. This opens new opportunities for extending UBI across diverse search implementations.
